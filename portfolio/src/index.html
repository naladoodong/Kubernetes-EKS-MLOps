01 · Engineering challenges

The hard parts are lifecycle boundaries.

The platform handles four workflows with different data volumes, runtimes, failure modes, and ownership rules. Each boundary is made explicit instead of hidden inside one API process.

01

Large dataset upload

2 GB CSV/XLSX → S3 multipart → async processing

The API issues upload intent and presigned URLs; it never becomes the bulk file data path.

Protect API bandwidth and request lifetime
02

Long-running GPU training

12–24h training → Kubernetes Job → S3 checkpoint

GPU execution is isolated from the API and scheduled onto Karpenter-provisioned capacity.

Recoverable execution with independent scaling
03

Distributed consistency

PostgreSQL → outbox → SQS → controller

At-least-once delivery, conditional updates, and reconciliation handle partial failure.

Durable intent without exactly-once claims
04

Model serving boundary

Gateway → interface validation → KServe

Business policy and public contracts stay in the gateway; the runtime only loads and predicts.

Stable API contract across model versions

02 · Architecture overview

Control intent. Isolate execution.

Public traffic reaches only the Backend API and Inference Gateway. Control-plane workloads persist business intent in RDS; data-plane workloads perform the expensive execution.

A

Control Plane

Owns business state, validates intent, publishes durable events, and reconciles observed execution.

B

Data Plane

Runs dataset processing, GPU training, and model inference against immutable objects in S3.

C

Source of Truth

RDS stores business state. SQS accelerates work; Kubernetes reports execution. Neither replaces RDS.

04 · Reliability & distributed systems

Designing for the state between systems.

The architecture does not attempt to eliminate distributed inconsistency. It defines how each component observes, retries, and converges on RDS business state.

OUTBOX

Transactional event intent

Business changes and OutboxEvent commit in one PostgreSQL transaction. Publishing happens afterward.

Retention: published 30 days → cleanup; unpublished never auto-deleted

CAS

Conditional state transition

Expected current state is part of each update, preventing stale controllers from overwriting newer facts.

Guard: rows affected must equal one

RECONCILE

Repair-path convergence

The initial 60-second loop compares RDS intent with Kubernetes observations. It is a repair path, not event latency or a user-facing SLO.

Shorter: more polling load · Longer: more recovery lag

CHECKPOINT

Bounded recomputation

Long GPU runs persist resumable checkpoints in S3, reducing interruption risk and recovery cost.

Rule: Job completion is not business success

training_jobs.sql atomic transition 
UPDATE training_jobs
SET status = 'RUNNING'
WHERE id = :job_id
  AND status = 'SCHEDULING';

Why it matters

A single conditional update advances only the transaction that still matches the current state.

TrainingJob state machine

Business state advances only from a valid predecessor.

Every state change and TrainingJobEvent commit together. Kubernetes completion is observed before the business record becomes terminal.

QUEUED → SCHEDULING → RUNNING → SUCCEEDED
Failure path QUEUED / SCHEDULING / RUNNING → FAILED
Cancellation race Active state → CANCEL_REQUESTED → terminal observation → CANCELLED · SUCCEEDED · FAILED

A cancellation request is intent, not an immediate terminal fact: a Job that completed before cancellation was observed can still converge to SUCCEEDED.

Exactly-once is not the claim. Durable intent, idempotent effects, and reconciliation are the design.

06 · Architecture decisions & trade-offs

Decisions carry consequences.

Eight adopted decisions show how requirements become operating responsibilities. Alternatives deferred for lack of workload evidence remain visible below.

Adopted decisions

Architecture complexity is introduced only when backed by workload requirements.

ADR 001

Amazon EKS

Decision
Use EKS as the target runtime.
Why
Unify Jobs, GPU scheduling, KServe, and policy.
Trade-off
Cluster and controller operations become platform responsibilities.

ADR 002

Control / Data Plane

Decision
Separate orchestration from execution.
Why
Different workloads need different failure and scaling boundaries.
Trade-off
Observed execution must be reconciled with business state.

ADR 008

Kubernetes GPU Job

Decision
Run 12–24 hour training as a Job.
Why
Isolate lifetime, GPU requests, retries, and timeout.
Trade-off
Job completion still requires business-level finalization.

ADR 006 / 028

SQS + Transactional Outbox

Decision
Persist event intent with the domain change.
Why
Avoid the DB / queue dual-write gap.
Trade-off
Duplicate delivery requires idempotent consumers and cleanup.

ADR 009

Karpenter GPU capacity

Decision
Keep core nodes stable; provision GPU nodes on demand.
Why
Match intermittent expensive capacity to pending Jobs.
Trade-off
Cold capacity adds scheduling delay and disruption policy work.

ADR 012 / 013

KServe Standard Mode

Decision
Keep KServe cluster-local behind the Inference Gateway.
Why
Separate business contracts from model runtime execution.
Trade-off
No scale-to-zero; active deployments keep at least one replica.

ADR 003 / 016

PostgreSQL / S3 / Athena

Decision
Separate OLTP, immutable objects, and analytical scans.
Why
Protect transactional performance and scale large data independently.
Trade-off
Catalog freshness and cross-store lifecycle need governance.

ADR 022

Modular monolith

Decision
Keep one codebase with separable process roles.
Why
Preserve domain boundaries without premature service sprawl.
Trade-off
Logical components are not all independently deployable yet.

Deliberately not adopted

Architecture quality is not measured by the number of technologies adopted.

Components were excluded when the requirement or measured bottleneck did not justify the additional state, failure modes, and operator workload.

RedisNo demonstrated RDS lookup bottleneck or cache invalidation requirement.
KEDAThe Training Controller already consumes SQS and creates Jobs.
KnativeNo scale-to-zero or long-streaming requirement for tabular inference.
Envoy GatewayALB, Inference Gateway, and ClusterIP provide the required routing boundary.
CloudFrontNo static asset or globally cached download requirement in the platform scope.

Target design · Cost controls

Elasticity is bounded by explicit operating rules.

These are architecture guardrails, not production cost measurements. They constrain expensive capacity while preserving a conservative reliability baseline.

01Scale GPU nodes to zero

No training demand means no standing GPU worker capacity.

02Cap aggregate GPU capacity

Karpenter NodePool limits bound the maximum GPU footprint.

03Default to On-Demand

The baseline favors predictable long-job continuity over discounted interruption risk.

04Gate Spot adoption

Spot is considered only after checkpoint and retry behavior is validated.

05Accept warm serving cost

KServe Standard Mode keeps active deployments at one or more replicas to reduce operational complexity.
